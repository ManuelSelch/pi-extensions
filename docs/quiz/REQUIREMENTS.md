# Quiz extension — Requirements

## Goal
Provide a small, dedicated question-and-reasoning interaction for the existing teach skill. Replace its generic two-question ask_user sequence without building a learning platform. The extension collects evidence; the agent remains the teacher.

## Requirements
- **R1** — Add an agent-callable `quiz` tool through a native `quiz/index.ts` extension in this repository. Each call handles exactly one question and waits for submission or cancellation; it does not generate or launch subsequent questions automatically.
- **R2** — Support single-choice questions with stable option identifiers and one selected answer. Include a distinct “I don't know” response that is not cancellation. Reject empty prompts, empty or duplicate option labels/identifiers, and otherwise malformed questions before opening UI. The agent must prepare exactly one correct option and vary its position; the tool cannot establish semantic correctness.
- **R3** — Collect optional multiline reasoning alongside the answer using the prompt “Explain how you reached your answer. What assumptions or uncertainties do you have?” Preserve the learner's submitted text; an empty explanation remains empty and is never synthesized.
- **R4** — Return a structured result identifying the question, displayed options, selected option or “I don't know”, reasoning, and explicit submitted/cancelled status. Cancelled drafts must not be represented as submitted evidence. Cancellation, unavailable UI, and invalid input must remain distinguishable.
- **R5** — Do not reveal the current question's solution or correctness indicator in its question interaction. Feedback on an already submitted previous question may be displayed, but the next check must not simply repeat an answer that feedback reveals. The teach skill must settle its expected answer, rationale, and acceptance criteria before asking, wait for the result, then evaluate answer and reasoning together. This is an instruction-level commitment, not secret or tamper-proof answer storage.
- **R6** — Keep teaching policy in the teach skill: cover one small objective with automatic adaptive progression, using about three cycles as a checkpoint rather than an automatic finish; distinguish sound reasoning, lucky selections, partial understanding, and misconceptions; adapt examples and hints; require explanation and a materially different application before claiming understanding. Cancellation is never graded as wrong, and revealed solutions are not independent success.
- **R7** — Support the user's existing Pi Chat implementation as a first-class client, as well as terminal Pi. Pi Chat currently forwards select/input/confirm/editor through pi-server's web UI context, but custom() resolves to undefined. The MVP must use supported dialogs without requiring Pi Chat/server/SDK changes. Never silently substitute ordinary chat, claim a combined form when using separate dialogs, or interpret missing/unsupported UI as learner cancellation. Q1 and Q2 are resolved: use separate choice and reasoning dialogs on both clients.
- **R8** — Keep submitted evidence in ordinary Pi tool results and their structured details. Do not add a database, cross-session learner profile, scores, mastery percentages, question bank, timers, background processes, or durable pending-question lifecycle. A reload or process exit need not resume an unfinished interaction; do not promise otherwise.
- **R9** — Update the existing teach skill to use `quiz` for supported single-choice checks and accurately describe its limitations. Retain generic ask_user interactions for session setup, Continue/Take a break/Finish checkpoints, and free-recall questions. If quiz is unavailable, disclose this and ask whether to use the existing ask_user sequence; do not fall back silently. Do not modify ask-user itself.
- **R10** — Verify question validation, answer/option identity, empty and multiline reasoning, “I don't know”, cancellation, unavailable UI, abort cleanup, and absence of solution disclosure. Include native extension registration and a manual interaction check for each supported mode. Terminal-specific UI must additionally be checked with keyboard-only navigation, narrow widths, resizing, Unicode, and focus restoration.
- **R11** — Automatically progress through adaptive checks on one small topic without requiring a “Next” message between questions. Continue until the learner demonstrates understanding through sound reasoning and a materially different application without a revealing hint; correct selections alone are insufficient. Keep explanations readable when a subsequent prompt opens. Recommended presentation, pending Q4: include concise feedback on the preceding submitted answer above the new question in the select dialog, and retain it as context in the reasoning dialog. Also provide feedback in the ordinary transcript. Do not infer reading completion from a timer. At about three checks or repeated confusion, offer Continue/Take a break/Finish or a change of explanation instead of an unbounded automatic loop. Cancellation stops the sequence. The agent controls adaptation and continuation; the collection tool does not grade or run a teaching loop itself.
- **R12** — Verify compatibility through the actual Pi Chat/server dialog bridge: choice followed by multiline editor, empty reasoning submission, cancellation during either stage, and automatic progression with previous-answer feedback readable inside the next prompt as well as in the transcript (subject to Q4). Verify a final explanation when no next question is needed, evidence-based completion, and a checkpoint when understanding remains uncertain. If the reasoning stage is cancelled, the earlier selection is a draft, not a submitted quiz answer.

## Assumptions
- The existing teach skill at `~/.pi/agent/skills/teach/SKILL.md` is the behavioral source of truth. Its current prohibition on building learning infrastructure concerns ordinary teaching sessions; this explicit extension-planning request authorizes planning a narrowly scoped replacement interaction, not implementing it yet.
- Confirmed interaction (Q1/Q2): use choice followed by reasoning dialogs on both terminal Pi and Pi Chat. Completing the reasoning stage, including an explicitly submitted empty explanation, submits the question. Do not add a separate TUI-only combined form to the MVP. This supersedes the earlier combined-terminal-form recommendation.
- Source inspection: Pi Chat's src/web/extensions/prompts/PromptModal.tsx immediately displays incoming prompts in a focus-trapped Mantine modal and keeps answered prompts mounted for a 400 ms handover window. That delay prevents menu flicker; it is not a reading checkpoint. The pi-server src/runtime/pi/web-ui-context.ts bridge supports separate select/editor dialogs and intentionally has no custom-terminal-component support.
- Proposed readable-feedback presentation (Q4): use ordinary human-readable multiline dialog titles, already rendered as heading plus body by PromptModal. Put previous-answer feedback and then the new question in clearly labeled sections; do not encode JSON or require frontend parsing. Repeat the question and relevant feedback in the reasoning dialog. Pi Chat renders this body as plain text, not Markdown/KaTeX; rich mathematical explanations may therefore need the optional minimize/reopen fix or a separately scoped UI change. No fixed delay can reliably establish that an explanation has been read.
- Optional future Pi Chat usability fix, not part of the extension MVP: let users minimize and reopen pending dialogs without responding or cancelling. The server request stays pending; the minimized UI must release focus trapping and expose a visible pending-question control. Preserve pending state across snapshots and scope presentation state to session/prompt identity; do not silently reset it on snapshots. Inspect existing timeout/disconnect behavior before promising indefinite reading time. This should remain a generic prompt fix, not a new frontend extension framework.
- A fully combined browser form would require a separately approved typed form request/result capability across pi-server, the SDK contract, an extension-accessible host API, and Pi Chat rendering. Modifying PromptModal alone cannot make ctx.ui.custom() serializable. Do not hide structured form data in dialog titles or special-case quiz tool names in the frontend.
- Single-choice checks are sufficient for the first version. Free recall continues through ask_user; multi-select, automatic grading, slash commands, and hint buttons are outside the MVP.
- The agent does not pass an answer key to the collection tool. It retains the prepared solution in its own reasoning/context; no secrecy, immutable rubric, or secure examination guarantee is implied.
- Existing repository folder, test inventory, and shared dependency conventions apply. Installed Pi and repository SDK versions must be checked rather than assumed identical.

## Open Questions
- **Q1** — Resolved: keep choice and reasoning separate on both terminal Pi and Pi Chat; defer a combined form and its cross-project changes.
- **Q2** — Resolved: the extension must work with the user's existing Pi Chat implementation. Terminal-only support is insufficient. Current Pi Chat supports standard select/editor dialogs, not custom terminal forms.
- **Q3** — Resolved: automatically ask a few adaptive questions covering one small topic, continuing toward demonstrated understanding rather than waiting for “Next” between checks. Preserve pause/finish checkpoints and do not claim understanding without evidence.
- **Q4** — Should the next question's popup also show feedback on your previous answer above the new question (recommended, no Pi Chat changes), or do you prefer a Pi Chat change that lets you minimize/reopen the pending popup to read the full chat explanation?
