# Workflow Extension — Requirements

## Goal
Give the user independent control over the mock, plan, design, and commit workflow instructions. Extract those instructions from always-present guidance into editable prompt files, activated through a small Pi extension with global configuration and per-project overrides.

## Requirements
- **R1** — Support independently enabling and disabling `mock`, `plan`, `design`, and `commit`, all enabled globally by default. Multiple steps may be enabled together; these are instruction switches, not an automatically advancing state machine. Disabled means no requirement to perform that step, not a prohibition on an explicit user request.
- **R2** — Read `<agent-dir>/workflow.json` and an optional `<session-cwd>/.pi/workflow.json`. Use Pi's session working directory, not the session-storage directory, Git repository root, or ancestor search. Project settings override only explicitly supplied fields; omitted fields inherit, and explicit `false` disables an inherited step. Document defaults, lookup boundaries, and precedence. Use an unversioned configuration with no schema migrations or backward-compatibility layer.
- **R3** — Keep prompt text in ordinary editable Markdown files outside extension source. Configuration associates each step with its prompt file and enabled state. Resolve relative paths against the configuration file declaring them. A project may override a step's enabled state, prompt file, or both without copying unrelated settings.
- **R4** — `/workflow` opens a small interactive selection popup listing mock, plan, design, and commit with their current enabled states. Let the user toggle multiple steps, then Save or Cancel; Escape cancels without writes. Persist saved changes to project configuration by default, with explicit global scope and a way to restore inherited project enablement; do not add session-only overrides. Preserve untouched fields, including prompt and skill associations. Show effective enabled states, configuration provenance, and resolved prompt paths through inspection. Use Pi's native selection dialog, usable in both TUI and RPC; manual on/off commands are not required.
- **R5** — Provide a way to inspect the exact composed workflow instructions before use. Editing prompt text or prompt settings takes effect on the next agent run without restarting Pi. Skill availability changes require startup or `/reload` (R11). Define a stable composition order and include each enabled prompt once; repeated runs must not accumulate duplicate instructions.
- **R6** — Update only the extension-owned workflow prompt section, preserving Pi's other instructions and other extensions' sections. Turning a step off removes it from subsequent active workflow injection; it cannot erase previously read instructions, conversation history, or higher-priority instructions. Explain this limitation when changing settings in an active session and recommend a fresh session for a clean context; do not promise that disabling a step immediately changes agent behavior.
- **R7** — Inventory and migrate existing workflow mandates so they are not still injected or automatically reintroduced elsewhere when a step is disabled. Preserve specialist guidance that is not a workflow gate. In particular, separate mandatory plan/design gates from developer implementation guidance and review skill descriptions and cross-links, not only skill bodies. Migration of personal files requires explicit approval and a reversible backup.
- **R8** — Diagnose malformed configuration and missing/unreadable enabled prompts with the responsible path. Never overwrite invalid configuration or silently use a conflicting fallback. Disabled prompts need not exist. Reject invalid command writes without modifying files; valid writes preserve unrelated settings and avoid partial files or lost concurrent updates.
- **R9** — Respect Pi's project-trust boundary before loading project configuration or project-selected prompt content. Prompts are trusted instructions, not executable templates. Do not evaluate code or interpolate shell commands.
- **R10** — Keep the initial extension limited to prompt and skill selection, prompt composition, inspection, and settings management. Do not add approval tracking, automatic stage transitions, tool blocking, autonomous commits, or a general workflow engine. An enabled commit prompt guides the agent; toggling it never directly executes Git commands.

- **R11** — Each step may select a prompt, skills, or both. Add enabled steps' skills through Pi's native `resources_discover` event using `skillPaths` at startup and `/reload`, keeping full skill bodies lazy-loaded. Store managed skills outside automatically scanned skill directories, preserving supporting files and relative links. Project skill lists replace inherited lists; an empty list selects no skills. Show configured versus last-discovered workflow skill selections and any reload requirement; reloading cannot remove instructions already read into conversation history.

## Assumptions
- The agent directory normally resolves to `~/.pi/agent`; honor Pi's configured agent directory rather than hard-coding the home directory.
- Proposed prompt locations: `<agent-dir>/workflow/prompts/` and optional project `.pi/workflow/prompts/`. These are not Pi's slash-command prompt-template directory and are not automatically discovered skills.
- The primary interface is `/workflow` with native selectable checkmarked rows, Save, Cancel, and a project action to restore inherited enablement. Native select returns one choice at a time, so toggling a row reopens the dialog with updated checks; this is not a custom multiselect widget. `/workflow global` edits global defaults; inspection and composed-prompt preview remain auxiliary commands. No custom editor or dashboard is necessary.
- Proposed composition order is mock → plan → design → commit. Prompts describe when each enabled step applies; enabling mock does not require mockups for unrelated backend tasks.
- Current inspected sources include `skills/mockup-first/SKILL.md`, `skills/roles/analyst/SKILL.md`, `skills/roles/developer/SKILL.md`, and `skills/roles/design-writing/SKILL.md` under the agent directory. The inspected global `AGENTS.md` contains memory instructions, not workflow gates; no global `SYSTEM.md` or `APPEND_SYSTEM.md` was found. Additional system-level instructions may come from the invoking client.
- Stored user preferences also contain mandatory planning-skill guidance and automatic-commit guidance. These are migration inputs, not instructions the extension can simply override. Selectively moving workflow mandates out of memory must preserve unrelated preferences and follow memory-edit policies.
- The inspected installed Pi documentation supports structured prompt sections through `before_agent_start`. This repository declares an older SDK range; compatibility must be checked during design rather than assuming identical APIs.

## Implementation Plan
### S1 — Configuration and prompt files
Description: Implement R1–R3 and configuration validation from R8 using the resolved Q1–Q3 decisions. Define the unversioned schema, defaults, field-level override semantics, prompt/skill selection, path resolution, and project boundary (including R11's skill-list replacement). Verify inheritance, explicit false, partial overrides, relative paths, malformed files, and absent optional configuration with isolated fixtures. No live personal prompts are changed.

### S2 — Prompt composition and injection
Description: After S1, implement R5, R6, R9, and the R10 runtime boundary. Compose enabled prompts in a stable order and update only the workflow-owned prompt section at the next agent-run boundary. Implement R11's native skill discovery at startup/reload, including removal on reload and shared-path deduplication. Verify repeated runs, prompt edits, disabling/removing all prompts, preservation of unrelated sections, trusted versus untrusted projects, and enabled-prompt read failures against the supported Pi runtime. Do not introduce a legacy SDK fallback unless a supported-runtime decision requires it.

### S3 — Workflow controls
Description: After S1 and S2, implement R4 and settings writes from R8. Add the native selection popup with staged toggles, Save, Cancel/Escape, explicit global scope, and restoration of inherited project enablement. Keep status and exact prompt preview as auxiliary commands, usable in TUI and RPC without custom terminal components. Report R11's configured versus last-discovered skill selections and pending reloads. Verify multiple toggles, save/cancel/no-op behavior, provenance, scope isolation, untouched-field preservation, invalid-write protection, concurrent-write behavior, and next-run activation. No model-callable settings tool is required for the initial version.

### S4 — Prompt extraction and migration
Description: After S2 and S3, implement R7 with an approved source-by-source migration checklist and backups. Extract workflow mandates into the four prompt files, relocate managed skills outside automatic discovery with their supporting files and valid relative links, remove duplicate automatic triggers and conflicting cross-step gates from their original sources, and preserve useful specialist content. Reconcile workflow-related memory preferences and any client-supplied instructions with the user. Verify all-off and individual-step configurations in fresh sessions so previously loaded skill text does not mask migration failures; document existing-session limitations and manual invocation. Do not claim a step is fully optional while another active source still mandates it.

## Open Questions
- **Q1 — Resolved:** All four steps are enabled globally by default.
- **Q2 — Resolved:** Use the session working directory, the simplest lookup consistent with Pi's project configuration convention. Read only `.pi/workflow.json` directly beneath it; do not search ancestors or infer the Git root.
- **Q3 — Resolved:** Persist toggles to project configuration by default, with explicit global scope available and no session-only state. Existing context may retain previous instructions; recommend a fresh session for clean behavior.
